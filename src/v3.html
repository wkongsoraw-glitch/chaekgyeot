00

시작하기 전에 — 우리 둘의 역할

웹사이트를 만드는 일에서 디퍼님이 맡을 몫과 제가 맡을 몫은 처음부터 다릅니다. 디퍼님은 무엇이 어떻게 보였으면 하는지를 정합니다. 저는 그 말을 코드로 옮깁니다. 그래서 코드를 직접 쓰실 필요는 없습니다.

다만 읽을 줄은 아셔야 합니다. 코드가 무슨 말인지 대강 알아야, 화면을 보고 "여기 이 부분을 이렇게 바꿔 달라"고 정확히 말할 수 있습니다. 글로 치면 조판을 직접 하지 않더라도 판면을 볼 줄은 아는 것과 같습니다. 이 권이 목표로 하는 건 딱 그만큼입니다.

이 권을 읽는 법

1장부터 4장까지는 순서대로 읽으시면 좋겠습니다. 30분이면 됩니다. 5장부터는 그때그때 필요할 때 펴 보시면 되는 자리입니다. 7장(저에게 말 거는 법)은 실제로 만들기 시작한 날 다시 읽으시면 훨씬 잘 붙습니다.

중간에 막히면

모르는 단어가 나오면 그냥 저에게 "그게 뭐야?"라고 물어 주세요. 무언가를 망가뜨릴까 봐 걱정되실 텐데, 이 작업에서 되돌릴 수 없는 일은 거의 없습니다. 파일 하나를 지워도 다시 만들면 그만입니다. 이 점이 글쓰기와 좀 다릅니다.

01

웹사이트는 결국 폴더 하나다

가장 먼저 내려놓으셔도 좋은 오해가 하나 있습니다. 웹사이트는 어떤 특별한 장치나 프로그램이 아닙니다. 파일 몇 개가 든 폴더입니다. 우리가 문서 폴더에 원고 파일을 모아 두는 것과 형태가 똑같습니다.

다른 점은 그 폴더를 읽는 쪽입니다. 원고는 사람이 읽지만, 이 폴더는 브라우저가 읽습니다. 크롬이나 사파리가 폴더 속 파일을 열어, 거기 적힌 지시대로 화면에 글자와 그림을 그립니다. 브라우저는 낭독자에 가깝습니다. 우리가 쓴 것을 화면이라는 목소리로 읽어 줍니다.

파일 이름 뒤에 붙는 점

파일 이름 끝의 .html, .css 같은 부분을 확장자라고 합니다. 이건 그 파일이 어떤 종류인지 알려 주는 꼬리표입니다. 내용은 전부 그냥 글자입니다. 특별한 파일이 아니라, 이름을 그렇게 붙였을 뿐입니다.

파일맡는 일
index.html페이지에 무엇이 있는지 — 제목, 글, 링크, 사진
style.css그것들이 어떻게 보이는지 — 색, 글꼴, 여백
script.js무엇이 움직이는지 — 버튼을 누르면 일어나는 일
images/사진을 모아 두는 폴더

02

세 개의 언어: 뼈대 · 결 · 움직임

웹 페이지를 이루는 언어는 셋입니다. 이름이 낯설 뿐 역할은 단순하고, 서로 하는 일이 겹치지 않습니다.

언어맡는 것책에 비유하면
HTML무엇이 있는가 — 내용과 구조원고
CSS어떻게 보이는가 — 색·글꼴·여백조판과 장정
JavaScript무엇이 움직이는가 — 반응과 변화책장을 넘기는 손

세 언어의 관계는 이렇습니다. 같은 원고를 다른 조판으로 찍으면 완전히 다른 책이 되지만 글은 그대로입니다. HTML과 CSS의 관계가 정확히 그렇습니다. 내용은 하나인데 style.css 하나만 바꾸면 페이지의 인상이 통째로 달라집니다.

그리고 하나 안심하실 만한 사실이 있습니다. 개인 웹사이트는 대개 HTML과 CSS만으로 충분합니다. 글 목록이 있고, 소개가 있고, 연락처가 있는 사이트라면 JavaScript는 없어도 됩니다. 세 번째 언어는 나중에, 정말 필요해질 때 꺼내면 되는 것입니다.

03

HTML — 글에 뼈를 세우는 일

HTML의 문법은 사실상 한 가지 규칙뿐입니다. 내용을 태그로 감싼다. 태그는 꺾쇠 안에 든 짧은 단어이고, 여는 것과 닫는 것이 짝을 이룹니다.

<p>읽고 쓰는 사람입니다.</p>
 ↑                        ↑
여는 태그                닫는 태그 (슬래시가 붙습니다)

<p>는 문단(paragraph)이라는 뜻입니다. 이렇게 감싸면 브라우저는 "아, 이건 하나의 문단이구나" 하고 앞뒤에 적당한 여백을 두고 그립니다. 감싸는 태그를 <h1>으로 바꾸면 같은 글자가 큰 제목이 됩니다. 태그는 글자를 꾸미는 게 아니라 글자의 역할을 알려 주는 이름표입니다.

속성 — 태그에 딸린 정보

태그 안에 추가 정보를 적기도 합니다. 링크가 대표적입니다. 어디로 가는 링크인지는 href에 적습니다.

<a href="https://example.com">책방수북</a>
<img src="images/cover.jpg" alt="책 표지">

alt는 그림을 볼 수 없는 사람에게 그림 대신 읽어 줄 설명입니다. 눈이 불편한 독자와 검색엔진이 이 문장을 읽습니다. 그림마다 한 줄씩 써 두는 습관은 값이 큽니다.

실제로 쓰게 될 태그는 열 개 남짓

태그뜻쓰는 자리
<h1>~<h3>제목 (1이 가장 큼)사이트 이름, 글 제목, 소제목
<p>문단본문 한 덩어리마다
<a>링크다른 페이지·바깥 사이트로
<img>그림표지, 사진
<ul> <li>목록과 그 항목글 목록, 약력
<strong>강조굵게 보이는 부분
<br>줄바꿈시의 행갈이처럼 꼭 필요할 때만
<div>묶음여러 요소를 한 덩어리로 묶을 때
<header> <footer>머리·꼬리 영역맨 위 이름, 맨 아래 연락처

<img>와 <br>은 감쌀 내용이 없어서 닫는 태그가 없습니다. 예외는 이 정도입니다.

한 장의 완성된 페이지

지금까지의 것을 모으면 이미 한 페이지가 됩니다. 아래는 그대로 저장해서 열어 보실 수 있는 온전한 파일입니다.

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>디퍼</title>
</head>
<body>

  <header>
    <h1>디퍼</h1>
    <p>읽고 쓰고 기록하는 사람입니다.</p>
  </header>

  <h2>쓴 글</h2>
  <ul>
    <li><a href="works/first.html">여는 글</a> — 2026년 봄</li>
    <li>겨울의 목록 — 기록 모음, 준비 중</li>
  </ul>

  <footer>
    <p>연락 · hello@example.com</p>
  </footer>

</body>
</html>

새로 나온 부분만 짚겠습니다. <head>는 화면에 보이지 않는 정보를 담는 자리입니다. 브라우저 탭에 뜨는 이름(<title>), 한글 설정, 휴대폰 화면 대응(viewport) 같은 것들이 여기 들어갑니다. <body>가 실제로 보이는 부분입니다. 이 두 칸의 구분만 기억하시면 됩니다. 맨 위 <!DOCTYPE html>은 "요즘 방식의 HTML"이라는 표시로, 그냥 늘 첫 줄에 두는 문장입니다.

가장 흔한 세 가지 실수

닫는 태그를 빠뜨림 — 그 뒤의 글이 전부 제목처럼 커지거나 링크가 됩니다. 화면이 이상하면 여기부터 보시면 됩니다.
따옴표를 빠뜨림 — href=주소가 아니라 href="주소"입니다.
한글이 깨짐 — <meta charset="utf-8">이 빠졌거나, 파일이 일반 텍스트로 저장되지 않은 경우입니다.

04

CSS — 같은 글을 다르게 입히는 일

CSS의 문법도 한 문장으로 끝납니다. 어디를, 무엇을, 어떻게.

h1 { color: #1A46C8; }
 ↑     ↑        ↑
어디를  무엇을   어떻게

앞의 h1을 선택자라고 부릅니다. "페이지에 있는 모든 h1에게"라는 뜻입니다. 중괄호 안에는 속성: 값; 짝을 필요한 만큼 적습니다. 세미콜론으로 한 줄씩 끝맺습니다.

HTML에 CSS를 붙이는 법

style.css라는 파일을 같은 폴더에 만들고, HTML의 <head> 안에 이 한 줄을 넣습니다.

<link rel="stylesheet" href="style.css">

실제로 만지게 될 다섯 가지

CSS의 속성은 수백 개지만, 개인 사이트에서 실제로 손대는 건 이 다섯 무리입니다.

무엇을속성예
색color backgroundcolor: #333;
글꼴과 크기font-family font-sizefont-size: 18px;
여백margin paddingmargin: 40px 0;
폭max-widthmax-width: 680px;
줄 간격line-heightline-height: 1.8;

margin과 padding은 헷갈리기 쉬운 짝입니다. 액자를 떠올리시면 편합니다. padding은 그림과 액자 테두리 사이의 여백, margin은 액자와 옆 액자 사이의 거리입니다. 안쪽 여백과 바깥 여백입니다.

글이 읽히게 만드는 최소한의 CSS

아래 정도만 있어도 페이지는 충분히 읽을 만해집니다. 특히 max-width가 중요합니다. 이게 없으면 큰 화면에서 한 줄이 끝없이 길어져서, 읽는 눈이 다음 줄을 놓칩니다. 책의 판면 폭과 같은 이야기입니다.

style.css
/* 본문 전체 */
body {
  max-width: 680px;
  margin: 60px auto;
  padding: 0 20px;
  font-family: sans-serif;
  font-size: 17px;
  line-height: 1.8;
  color: #23262B;
  background: #FBF9F5;
}

/* 제목 */
h1 {
  font-size: 30px;
  margin-bottom: 4px;
}

/* 목록에서 점 없애기 */
ul {
  list-style: none;
  padding: 0;
}

li {
  padding: 8px 0;
  border-bottom: 1px solid #E7E2D9;
}

margin: 60px auto;에서 auto는 "좌우 여백을 알아서 똑같이 나눠라", 즉 가운데 정렬입니다. 두 개의 값은 각각 위아래와 좌우를 뜻합니다. /* 이렇게 */ 감싼 부분은 주석입니다. 화면에는 보이지 않고, 나중에 다시 읽을 나를 위한 메모 자리입니다.

한글 글꼴 이야기

한글 웹폰트는 글자 수가 많아 파일이 무겁습니다(영문 폰트의 수십 배). 예쁜 폰트를 여럿 얹으면 사이트가 눈에 띄게 느려집니다. 본문용 하나, 제목용 하나 — 두 벌이면 충분하고, 그 이상은 대개 사이트를 느리게만 만듭니다.

05

이름과 길: 파일명과 경로

여기서 겪는 문제는 대부분 문법이 아니라 이름을 잘못 지었거나 길을 잘못 알려 준 경우입니다. 사진이 안 뜨고 링크가 안 먹히는 일의 십중팔구가 이쪽입니다.

index.html이라는 이름

이 이름은 약속입니다. 누군가 주소창에 mysite.com만 치고 들어오면, 서버는 그 폴더에서 index.html을 찾아 보여 줍니다. 그래서 대문 페이지의 이름은 반드시 index.html이어야 합니다. home.html이나 메인.html로 지으면 빈 화면을 만나게 됩니다.

이름 짓는 규칙

  • 영문 소문자만 씁니다. 한글 파일명은 주소창에서 알아볼 수 없는 문자로 바뀝니다.
  • 띄어쓰기 대신 하이픈을 씁니다. 오늘의 기록.html이 아니라 today-note.html.
  • 사진 파일도 마찬가지입니다. IMG_2891 복사본.JPG는 cover-2026.jpg로 바꿔서 넣습니다.

폴더의 생김새

my-site/
├── index.html          ← 대문
├── about.html          ← 소개
├── style.css           ← 전체 디자인
├── images/
│   └── cover.jpg
└── works/
    └── first.html      ← 글 한 편

경로 — 파일에게 알려 주는 길

파일이 서로를 부를 때는 자기 자신을 기준으로 길을 적습니다.

이렇게 쓰면이런 뜻
style.css나와 같은 폴더 안에 있는 파일
images/cover.jpg내 옆의 images 폴더 안으로 들어가서
../style.css한 칸 밖으로 나가서 (점 두 개가 "밖으로")
https://…완전히 다른 사이트로

그래서 works/first.html에서 대문의 style.css를 부르려면 ../style.css라고 적어야 합니다. 한 칸 밖으로 나가야 하니까요. 사진이 깨져 보이면 대개 이 점 두 개가 빠졌거나 남았습니다.

06

인터넷에 올리기 — 주소가 생기는 순간

지금까지 만든 파일은 디퍼님 컴퓨터 안에만 있습니다. 남이 보려면, 24시간 켜져 있는 남의 컴퓨터에 그 폴더를 올려 두어야 합니다. 그 컴퓨터를 서버라고 부릅니다. 여기서 세 단어가 나옵니다.

단어뜻비유
호스팅파일이 놓이는 자리를 빌리는 것가게 자리
도메인사람이 외우는 주소가게 간판
배포내 폴더를 그 자리에 올리는 행위진열

실제 선택지

둘 중 하나를 고르시면 됩니다. 코드를 아예 만지지 않는 길과, 우리가 만든 폴더를 올리는 길입니다.

방법비용품어떤 경우에
Netlify Drop
netlify.com/drop		무료5분만든 폴더를 창에 끌어다 놓으면 끝. 첫 배포로 가장 좋습니다
GitHub Pages무료한나절수정 이력이 남습니다. 나중에 옮겨도 좋습니다
Vercel무료반나절사이트가 커지면 편해집니다
아임웹 · 노션월 0~3만원반나절코드 없이 마우스로. 대신 형태가 정해져 있습니다

디퍼님께는 Netlify Drop부터 권합니다. 회원가입 없이도 폴더를 끌어다 놓기만 하면 그 자리에서 주소가 하나 생깁니다. 내가 만든 것이 세상 어디서나 열린다는 감각을, 첫날에 한 번 겪어 보시는 편이 좋습니다. 그 뒤의 모든 공부가 훨씬 구체적인 일이 됩니다.

주소를 사는 일

처음 받는 주소는 brave-fox-3f21.netlify.app처럼 임시로 붙은 이름입니다. 내 이름의 주소를 갖고 싶으면 도메인을 삽니다. 가비아나 후이즈 같은 곳에서 사고, .com은 대략 연 1만 5천 원에서 2만 원 선, .kr은 조금 더 저렴합니다. 매년 갱신하는 방식입니다.

다만 도메인은 급하지 않습니다. 사이트가 어느 정도 형태를 갖춘 뒤에 사도 늦지 않고, 이름을 정하는 데에도 시간이 걸리니까요.

07

저에게 말 거는 법

실제로 만드는 동안 디퍼님이 가장 많이 하실 일은 코드를 쓰는 게 아니라 저에게 말하는 것입니다. 그래서 이 장이 이 권에서 가장 실용적인 자리입니다.

요청이 잘 전해지려면 세 가지가 있으면 됩니다. 어디를 · 무엇이 · 어떻게. "예쁘게 해 줘"보다 "제목 아래 여백이 좁아 보여, 두 배쯤 넓혀 줘"가 훨씬 빨리 원하는 곳에 닿습니다. 원고에 빨간 펜으로 표시하듯 말씀하시면 됩니다.

그대로 쓰셔도 되는 문장들

처음 만들 때
"제 개인 사이트를 만들고 싶어. 첫 화면에는 이름, 짧은 소개, 쓴 글 목록, 연락처가 있으면 좋겠어. 분위기는 조용하고 여백이 넉넉했으면 해."
완성된 그림이 없어도 괜찮습니다. 들어갈 것을 나열하고 분위기를 한 낱말로 얹어 주시면 첫 화면이 나옵니다. 거기서부터 고치는 편이 처음부터 정하는 것보다 쉽습니다.
고치고 싶을 때
"글 목록에서 제목과 설명 사이가 너무 붙어 있어. 조금 띄워 줘."
위치(글 목록에서) · 대상(제목과 설명 사이) · 방향(띄워 줘). 이 세 조각이면 충분합니다. 수치는 모르셔도 됩니다.
참고할 것이 있을 때
"이 사이트처럼 글 목록이 날짜순으로 쭉 늘어선 형태가 좋아. 주소는 여기야: …"
좋아하는 사이트 주소를 던져 주시는 게 형용사 열 개보다 정확합니다. 마음에 든 부분만 콕 집어 주시면 더 좋습니다.
화면이 이상해졌을 때
"이렇게 나왔어" — 그리고 화면에 뜬 글자를 통째로 붙여넣기
영어로 길게 뜨는 빨간 글씨는 읽지 않으셔도 됩니다. 요약하지 말고 그대로 복사해 주시는 게 가장 좋습니다. 대부분 어디가 잘못됐는지 그 안에 적혀 있습니다.
되돌리고 싶을 때
"방금 바꾼 거 되돌려 줘. 그 전이 나았어."
언제든 하셔도 되는 말입니다. 미안해하실 일이 전혀 아니고, 오히려 이 말을 자주 하시는 편이 결과가 좋습니다.
무슨 일이 일어났는지 모르겠을 때
"지금 뭘 한 건지 한 문장으로 설명해 줘."
이해가 따라가지 못한 채로 쌓이면 나중에 혼자 고치기 어려워집니다. 물어보시는 만큼 사이트가 디퍼님 것이 됩니다.
방향이 흐려질 때
"지금까지 만든 걸 정리해 주고, 다음에 뭘 하면 좋을지 세 가지만 알려 줘."
여러 날에 걸쳐 만들다 보면 어디까지 왔는지 흐려집니다. 이 말로 한 번씩 매듭을 지으시면 좋습니다.

백업이라는 습관

큰 변화를 주기 전에 my-site 폴더를 통째로 복사해 두시길 권합니다. my-site-0827처럼 날짜를 붙여 두면 됩니다. 원고를 고치기 전에 다른 이름으로 저장해 두는 것과 똑같은 습관이고, 이유도 똑같습니다. 나중에는 Git이라는 더 나은 방법을 쓰게 되겠지만, 지금은 이 정도로 충분합니다.

08

자주 마주칠 단어 스물넷

대화 중에 튀어나올 때 당황하지 않으실 만큼만 적었습니다. 외우지 마시고, 나올 때마다 돌아와 보시면 됩니다.

브라우저 browser
크롬·사파리처럼 웹 페이지를 읽어 화면에 그려 주는 프로그램.
서버 server
내 사이트 파일을 대신 갖고 있으면서 요청이 오면 내주는, 늘 켜져 있는 컴퓨터.
로컬 local
내 컴퓨터 안. "로컬에서는 되는데"는 아직 인터넷에 안 올렸다는 뜻.
호스팅 hosting
서버에 자리를 빌리는 일. 개인 사이트는 대개 무료로 됩니다.
도메인 domain
mysite.com 같은 주소. 매년 돈을 내고 빌립니다.
배포 deploy
완성된 파일을 서버에 올려 세상에 보이게 하는 행위.
에디터 editor
코드를 쓰는 편집기. VS Code가 가장 흔합니다.
터미널 terminal
검은 화면에 명령을 글자로 적어 컴퓨터를 부리는 창. 무섭게 생겼지만 그냥 다른 방식의 대화창입니다.
깃 git
파일이 언제 어떻게 바뀌었는지 기록해 두고 언제든 되돌리는 장치. 원고의 모든 버전을 잃지 않는 방법.
깃허브 GitHub
그 기록을 인터넷에 보관해 주는 곳.
리포지토리 repository
깃허브에 올라간 프로젝트 폴더 하나. 줄여서 '레포'.
커밋 commit
"여기까지를 한 매듭으로 저장" 하는 것. 원고의 한 판본.
프레임워크 framework
같은 걸 매번 새로 짓지 않도록 미리 짜 둔 뼈대. React·Next.js 같은 이름들.
라이브러리 library
남이 만들어 둔 기능 꾸러미. 가져다 씁니다.
반응형 responsive
휴대폰에서도 화면이 알맞게 접히도록 만든 것. 요즘은 필수입니다.
렌더링 rendering
코드를 화면에 실제로 그리는 일.
캐시 cache
브라우저가 이전 화면을 기억해 둔 것. 고쳤는데 안 바뀌어 보이면 ⌘⇧R로 새로고침.
API
다른 서비스의 정보를 가져다 쓰는 창구. 지금은 몰라도 됩니다.
SEO
검색에 잘 걸리게 하는 일. 제목과 설명을 성실히 쓰는 게 절반입니다.
파비콘 favicon
브라우저 탭에 뜨는 작은 그림.
버그 bug
의도와 다르게 동작하는 부분. 잘못이 아니라 만드는 과정의 일부입니다.
디버깅 debugging
그걸 찾아 고치는 일. 시간의 대부분이 여기 쓰입니다.
오픈소스 open source
누구나 보고 가져다 쓸 수 있게 공개된 코드.
개발자 도구 DevTools
브라우저에서 ⌥⌘I로 열리는 창. 지금 보는 화면의 코드를 그대로 들여다볼 수 있습니다.
09

첫 2주, 하루 30분

한꺼번에 하지 않으셔도 됩니다. 하루 30분씩 2주면 인터넷에 자기 주소를 가진 사이트가 생깁니다. 순서는 쉬운 것에서 시작해 성취가 먼저 오도록 짰습니다.

1일차
1장 실습 — 첫 파일 열기index.html을 만들어 브라우저로 열어 봅니다. 오늘의 목표는 이것뿐입니다.
2일차
VS Code 설치무료입니다. 텍스트 편집보다 훨씬 편하고, 오타를 색으로 알려 줍니다.
3일차
3장의 페이지를 그대로 옮겨 적기복사가 아니라 손으로 쳐 보시면 태그가 몸에 남습니다.
4일차
내용을 내 것으로 바꾸기이름, 소개, 글 목록을 실제 내용으로. 이때 처음으로 '내 사이트' 같아집니다.
5일차
style.css 붙이기4장의 CSS를 그대로 넣고, 색과 글자 크기만 마음대로 바꿔 봅니다.

쉬기, 또는 좋아하는 사이트 모으기마음에 드는 사이트 세 곳의 주소를 적어 두시면 다음 주에 씁니다.

Netlify Drop으로 첫 배포폴더를 끌어다 놓습니다. 주소가 생깁니다. 여기가 이 2주의 고비이자 정점입니다.
9일차
휴대폰으로 열어 보기글자가 작거나 넘치는 곳을 찾습니다. 저에게 말씀하시면 고쳐 드립니다.
10일차
두 번째 페이지 만들기소개 페이지(about.html)를 만들고 대문에서 링크로 잇습니다.
11일차
글 한 편 올리기이미 써 두신 글 한 편을 페이지로 옮겨 봅니다. 여기서 사이트가 살아 있는 것이 됩니다.
12일차
사진 한 장 넣기images 폴더, 파일명 규칙, alt 설명 — 5장이 실제로 쓰이는 날입니다.
13일차
모아 둔 사이트를 참고해 결 다듬기글꼴, 여백, 색. 저에게 "이 사이트처럼"이라고 말씀하시면 됩니다.
14일차
주소 하나 정하기도메인은 나중에 사도 됩니다. 오늘은 이름만 정해 두셔도 충분합니다.
부록

지금은 몰라도 되는 것들

코딩을 배우려고 검색하면 금세 만나게 되는 이름들입니다. 하나같이 중요해 보이지만, 개인 웹사이트를 만드는 데는 지금 전혀 필요하지 않습니다. 몰라서 못 하는 게 아니라, 아직 쓸 자리가 없는 것들입니다.

이름언제 필요해지는가
React · Vue · Next.js페이지가 수십 장이 되고 화면이 복잡하게 움직여야 할 때
TypeScript코드가 커져서 실수를 미리 막아야 할 때
npm · 빌드 · 번들러남이 만든 도구를 여럿 조합해 쓸 때
데이터베이스 · 백엔드방문자가 글을 남기거나 로그인을 해야 할 때
Docker · CI/CD여럿이 함께 개발할 때
Tailwind · 디자인 시스템비슷한 화면을 여러 장 반복해 만들 때

이 이름들은 필요해지는 날 다시 찾아옵니다. 그때 배우면 훨씬 빨리 배워집니다. 쓸 자리를 이미 알고 있으니까요.

웹사이트를 만드는 일은 생각보다 글 쓰는 일과 닮았습니다. 처음에 쓴 것은 대개 마음에 들지 않고, 고치는 동안 형태가 잡히고, 어느 날 남에게 보여도 되겠다 싶은 순간이 옵니다.

다른 점이 있다면, 여기서는 언제든 되돌릴 수 있고 아무것도 영영 망가지지 않는다는 것입니다. 그러니 마음 편히 눌러 보셔도 됩니다. 막히는 자리에서 부르시면 됩니다.
